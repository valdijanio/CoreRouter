history: G1.24 feito (regras de negócio da GUI vindas do engine)

Comando novo `ip.firewall.actions {table?}`: devolve, por tabela, as cadeias embutidas, as
actions que a tabela aceita e, para cada uma, os parâmetros que ela recebe e as cadeias de onde
roda. As fontes são as mesmas que o `add`/`set` conferem (`corerouter_firewall::validate::
{table_actions, action_chains}`, agora públicas e usadas pela validação, e o `ACTION_FIELDS` do
engine).

A janela de regra do Firewall deixou de ter cópia própria (`FwTable::chains`, `FwTable::actions`,
`action_field_owner` e o "mark-* ou change-mss" do passthrough). Ela busca o esquema como as
outras abas (`Feed::Actions`) e mostra um campo de action só quando o engine diz que a action o
recebe. Sem o esquema (roteador antigo), o formulário manda o que foi preenchido e o engine
julga.

Achado no print e corrigido antes do PR: uma regra NAT com `accept` mostrava "Reject With" e os
campos de mangle, porque um campo de action de outra tabela contava como "matcher". O teste de
contrato foi reforçado para pegar esse caso.

Teste de contrato (`crates/ui/src/tests/firewall_actions.rs`): para cada action de cada tabela, o
formulário com todos os campos de action preenchidos manda exatamente os parâmetros que o engine
lista, e o engine não recusa nenhuma chave enviada; ao trocar de action, os parâmetros antigos
saem; nenhum parâmetro do engine fica sem campo na janela.

Como testar: `cargo test -p corerouter-ui firewall_actions`, `corerouter-cli run
ip.firewall.actions '{"table":"nat"}'`. Na GUI, Firewall › NAT › "+" › Action: as actions do NAT;
dst-nat mostra só To Addresses e To Ports.
